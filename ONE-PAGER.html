MVP · proof of concept

Engineering knowledge search, on one page

An engineering lead asks for a load limit, a material grade or an approval status, and gets the exact words from the file, with the file, the line and a fingerprint of the bytes. Below: the brief, the system, and the journey of one file through it.

Background

  • Years of design information sit in design files and project documents B1
  • Users do not know which file holds what they need B2
  • They will not learn file formats or schemas B3, query languages or jargon B4

Use case

A selected engineering manager or lead U1 finds a load limit, a material specification or an approval status U2 across 100+ project documents U3, in under 10 seconds U4, with 100% confidence in the source U5, without opening a CAD file or a PDF viewer U6.

Constraints (they already exist)

  • An architecture direction C1
  • A repository that holds the files C2
  • Connectors that extract metadata, text and properties C3
  • Structured and/or semantic stores C4
  • A chat-agent shell that calls tools C5

The MVP does not build these. It stands in for each only as far as the flow needs (amber below).

Scope

An MVP S1, not the final platform S2. Built: one search service behind an MCP server and a web test page; permissions before ranking; cited answers; constrained SQL; audit; an 8 s time budget.

Out of scope or open: semantic search O1, real identity G1, durable audit G2, many users and automatic refresh G5, an ontology G6, formats the stand-ins cannot read G8.

Where metadata comes from

  • Detector (file level): type, format version, size, from the extension and the first 512 bytes.
  • Indexer: the SHA-256 content fingerprint; the reader and its version.
  • Readers (file specific): headings, lines, pages and sheets; a DXF title block (drawing number, revision, approval) as a table.
  • Path: the file ID; the project from a project-<name> folder.
  • Not extracted: author, dates, repository revision. A real connector supplies them C3.

What the journey shows, and what it does not

  • The value, quoted, with file, line and fingerprint U2 U5 U6
  • Answered in tens of milliseconds over 145 indexed files U3 U4
  • No name, text or count from a file a user may not read K13
  • A changed file is never quoted stale K3

Not shown, because not built: real connectors and identity, a repository watcher, a semantic store, many users at once.
