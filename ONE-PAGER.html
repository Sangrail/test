MVP · proof of concept

Engineering knowledge search, on one page

An engineering lead asks for a load limit, a material grade or an approval status, and gets the exact words from the file, with the file, the line and a fingerprint of the bytes. Below: the brief, the system, and the journey of one file through it.

Codes such as B1 or K13 name items of the brief and of its analysis; each card below defines its own. Hover a code for its meaning, or see what every code means at the foot of the page.

Background (B)

  • B1 Years of design information sit in design files and project documents.
  • B2 Users do not know which files hold what they need.
  • B3 Users will not learn file formats or schema details.
  • B4 Users will not learn query languages or system jargon.

Use case (U): one use case, six parts

  • U1 A selected engineering manager or lead
  • U2 finds a load limit, a material specification or an approval status
  • U3 across 100+ project documents
  • U4 in under 10 seconds
  • U5 with 100% confidence in the source
  • U6 without opening a CAD file or a PDF viewer.

Constraints (C): what the brief assumes

  • C1 A broader architecture direction. MVP: one service behind tools and an HTTP API, so it can fit.
  • C2 A repository that holds the files. MVP: a test repository of 149 files, read in place.
  • C3 Connectors that extract metadata, text and properties. MVP: simple connectors built here, one reader per format plus fixed fact rules, to show the flow of information.
  • C4 Structured and/or semantic stores. MVP: one SQLite file with a full-text index, tables and facts.
  • C5 A chat-agent shell that calls tools. MVP: Claude Code, Codex or Pi through its MCP server.

Where the company's own version exists, it replaces the MVP's. The MVP's versions are kept deliberately straightforward (amber in the map).

Scope (S)

  • S1 An MVP.
  • S2 Not the final platform or solution.

Built: one search service behind an MCP server and a web test page; permissions before ranking; quoted, cited answers; constrained SQL; an audit log; an 8-second time budget.

Left open (G) or out of scope (O): G1 real identity, G2 durable audit, G5 many users and automatic refresh, G6 an ontology, G8 formats the MVP's readers cannot read, O1 semantic search.

Where metadata comes from

  • Detector (file level): type, format version, size, from the extension and the first 512 bytes.
  • Indexer: the SHA-256 content fingerprint; the reader and its version.
  • Readers (file specific): headings, lines, pages and sheets; a DXF title block (drawing number, revision, approval) as a table.
  • Path: the file ID; the project from a project-<name> folder.
  • Not extracted: author, dates, repository revision. The company's connectors would supply them C3.

What the journey shows, and what it does not

  • The value, quoted, with file, line and fingerprint U2 U5 U6
  • Answered in tens of milliseconds over 145 indexed files U3 U4
  • No name, text or count from a file a user may not read K13
  • A changed file is never quoted stale K3

Not shown, because not built: the company's own connectors and identity, a repository watcher, a semantic store, many users at once.
